## 入口与范围

相册 → 已完成的年龄照片 →「一生衣橱 · 为这张照片换装」。支持单人或双人合照，每次选择一个已生成年龄的一张照片，逐人选择衣着；完整内置八系列31款，目录和适用范围见 [一生衣橱模板目录](LIFETIME_WARDROBE_CATALOG.md)。原有日常、正装、中式三项仅为旧任务兼容保留。保持所选年龄、人物顺序、体型、姿态和背景，仅替换可见衣着。换装结果为独立副本，原来的1张或21张年龄照片不被覆盖；换装记录可从相册重新打开并回显原选择。

页面提供原片/结果对照、原图保存、失败恢复、刷新与单独撤回换装授权。请求状态不明时必须按原选择重放同一请求，不另起重复任务；隐藏/卸载后清理临时图片并忽略迟到响应。任务回执离页后才到达时，回到页面恢复原任务，不自动再次提交。

## 审查结论与复用

原项目只有年龄生成计划中的默认衣着约束，没有实际换装入口、编辑源绑定、单独授权或换装质量合同。本次复用已有 B14 外部命令、持久化 SQL、签名回调、B15/B17、时间轴查询、单节点重试和校验下载，不新增伪造的图像生成服务，也不扩张既有固定回调路由清单。B16 继续负责视频。

新 profile 为 `wardrobe-edit-v1`。服务端从已验收的年龄结果推导原始上传、原命令、有效恢复子命令、输出图片完整元数据、目标年龄和有序人物；客户端只能提交逐人服装选择。未就绪、来源错误、错人、错年龄、未知风格、跨所有者、冻结或需核对的来源均拒绝。源图内容读取并校验摘要后才创建换装请求；不能提交任意 URL、提示词、价格或自报质量决定。

`ltm.wardrobe-edit.v1` 与 `ltm.wardrobe-binding.v1` 固定父命令、来源图片 ID/SHA256、年龄、逐人衣着选择摘要。原图不能原样冒充换装结果。B15/B17 均须绑定这些编辑参数和新输出；换装质量额外要求服装匹配、非服装区域保持，每个人还须单独通过身份、年龄、五官漂移和服装匹配，不能用平均分或人工 override 掩盖失败。它们是严格的报告/发布合同，尚不是实际图像测量模型。

## 授权与撤回

沿用 `age_transformation` 处理目的，但必须额外授予独立的 `wardrobe` 动作，使用 `wardrobe-edit-consent-v1`。已有年龄生成的 ingest/transform 同意不能替代换装同意；原年龄授权和换装授权都必须有效。每人只可确认本人，情侣需独立确认。邀请页接受明确的 wardrobe 类型，未知类型拒绝，不授予公开分享权；分享邀请使用本地静态封面，避免自动截入私人照片。没有主动发送邀请。

原照衍生年龄照片的换装用途可单独撤回。创建、查询、保存、重试都复查授权与来源；worker 在真实网络出站前再次检查所有参与者的原年龄及换装同意，排队期间任一项撤回则不向供应商发送。页面的撤回操作只处理本人、本原照、换装动作的有效授权，不撤回年龄生成授权或对方授权。真实未成年参与者的监护关系仍由既有服务端权威校验，换装邀请不产生监护权。

部署时必须将实际披露文本摘要及该独立版本纳入既有签名同意目录。测试持有的 sandbox 目录只用于执行真实签名/范围校验，不是生产隐私批准；未配置有效目录时保持拒绝，不由客户端填写摘要。

## API 与保存

- GET/POST `/v1/timelines/{commandId}/nodes/{targetAge}/wardrobe`：取得受控上下文或创建独立换装请求；POST 请求体只接受 `selections`，必须有 Idempotency-Key。
- 使用返回的新 commandId 查询已有 `/v1/timelines/{commandId}`，其中 creationKind 为 wardrobe，并带原年龄来源；单张换装不冒充 21 张相册。
- 原图下载与最多三次显式恢复沿用原时间轴接口。恢复保留衣着、原图、两人引用和年龄；下载原字节并校验摘要、尺寸和文件长度，保存不再次压缩。

未新增 SQL 迁移、付费订单、收费金额、生产模型或供应商凭据。供应商必须识别新编辑合同、取到授权原图实际字节，并提供可信的换装质量测量与安全证据，不能把旧年龄接口的成功回执当作换装成功。
