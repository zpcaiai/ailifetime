# Integration gateway

The integration gateway accepts provider callbacks only after native signature validation. It preserves the exact request bytes, uses a tenant-and-route-bound Redis lease/outbox state machine, stores artifacts in KMS-encrypted S3 with Object Lock, and signs provider-bound evidence with an Ed25519 key from AWS Secrets Manager. Provider facts are submitted as one atomic `external-event.apply` command containing both the canonical business event and its evidence. Independent decisions needed by a later direct capability invocation are submitted as `evidence.register`; the runtime later consumes that single-use evidence in the same transaction as the gated capability mutation. A retry after an API failure reuses the same persisted event/evidence envelope, evidence ID, nonce, timestamps, signature, request body, and idempotency key; an expired envelope is atomically cleared and re-verified, while a corrupted cache entry is cleared and rejected.

Production startup is fail-closed. Configure `APP_ENV=production`, a fixed `LTM_TENANT_ID`, a `rediss://` `LTM_REDIS_URL`, the `LTM_EVIDENCE_S3_*` settings, the complete `LTM_PARTNER_WEBHOOK_POLICIES_REFERENCE`, `LTM_SUPPLY_EVENT_AUTHORITIES_REFERENCE`, and `LTM_DIRECT_EVIDENCE_AUTHORITIES_REFERENCE`, plus managed references for the evidence signing key and commerce-binding request/response keys. `LTM_API_COMMAND_URL` must end exactly in `/v1/commands`; `LTM_API_BEARER_TOKEN_FILE` must be an absolute projected workload-identity token file and is reread for every command. The workload principal needs exactly the deployed gateway permissions for `external-event:apply` and `evidence:register`, under the configured `LTM_API_EVIDENCE_PURPOSE`. Inline bearer tokens, evidence private keys, Apple roots, Google service-account JSON, and WeChat key material are rejected.

Google Play uses Application Default Credentials/workload identity by default. Set `LTM_GOOGLE_AUTH_MODE=managed-service-account` and `LTM_GOOGLE_SERVICE_ACCOUNT_REFERENCE=secret-manager:...` only when a managed long-lived key is explicitly required. Apple production requires online certificate checks and an Apple app ID. WeChat and store callbacks require the signed internal commerce-binding resolver; tenant, account, order totals, and currency are never accepted from callback URLs, query strings, or client headers. Partner webhook policies are loaded from `LTM_PARTNER_WEBHOOK_POLICIES_REFERENCE` and bind every core-owned external-command callback route to one concrete production authority.

The managed partner-policy document uses version `ltm.partner-webhook-policies.v2` and has a closed schema. It must contain exactly the 19 operations in core `EXTERNAL_COMMAND_CALLBACK_ROUTES` (18 capability dispatch routes plus the server-derived B10 `revokeExport` route); an unknown, duplicate, or missing route, an extra schema field, or a mismatched `batchId`/`operation`/`evidenceKind`/`provider` binding aborts startup. Each entry fixes the signature key/scheme, body/skew/retention limits, and native `commandId`, event ID, terminal state, occurrence time, sequence, and provider-operation paths. Its allowlist must cover `succeeded`, `failed`, `cancelled`, and `compensated`. Routes are fixed at `/v1/callbacks/partners/<routeId>`.

Only the command ID is read before verification to construct the evidence subject, and the signed payload must reproduce that exact subject. Event ID, terminal state, provider time, sequence, provider operation ID, and each route-owned `requiredClaimFields` identifier are resolved only after exact-body signature and native-policy validation by `verifyAndAttestExternalCommandTerminal`. The B10 revoke route requires `targetProviderOperationId`, which the reducer compares with the original provider share reference persisted in the revoke command. Tenant, collection, provider, subject/correlation shape, patches, terminal booleans, reducer choice, ledger entries, and command transition shapes are not callback inputs. Replay is claimed only after the artifact and signed business-event evidence have been created; the durable gateway delivery state publishes the resulting `external-event.apply` envelope once.

B99 shipment facts, B100 inventory adjustments and B102 vendor-scorecard facts have their own fixed callback routes because these capabilities reject direct writes and can exist only through `external-event.apply`: `/v1/callbacks/partners/b99-shipment-fact`, `/b100-inventory-fact`, and `/b102-scorecard-fact` under the same callback prefix. `LTM_SUPPLY_EVENT_AUTHORITIES_REFERENCE` points to a closed `ltm.supply-event-authorities.v1` document enrolling one or more exact `carrier:*`/`vendor:*` signers for every route. Each exact-body `ltm.supply-event.v1` payload is signature-, timestamp-, nonce-, tenant-, provider-, route-, subject- and artifact-bound. Event types and canonical claims use dedicated route schemas; inventory balances and scorecard metrics are reducer-derived and cannot be asserted by a provider payload.

The other direct evidence gates from B37 through B126 use 30 fixed routes under `/v1/callbacks/partners/evidence-<routeId>`. B127 is deliberately absent: only the independent release-control verifier may certify it. `LTM_DIRECT_EVIDENCE_AUTHORITIES_REFERENCE` points to a closed `ltm.direct-evidence-authorities.v1` document; startup rejects an unknown route, a missing one of the 30 routes, a duplicate route/provider signer, a provider outside the route's exact prefix/allowlist, an inline key, or unsafe skew/body/retention limits. An authority may submit either a route-fixed `ltm.direct-evidence-callback.v1` decision (`approved`, `passed`, `verified`, `published`, or `certified`, never an asserted boolean) or one of the five closed operational report schemas. Every callback carries the complete canonical `decisionRequest` and its SHA-256; the signed evidence scope includes that digest. Capability execution recomputes the same digest after validation, excluding only the evidence IDs/scope and the one signed artifact-digest field, so changing state, decision, action, amount, threshold, schema or target after issuance cannot reuse the evidence. Operational reports additionally cross-check their subjects, target fields and thresholds with that request. Nested decision claims are bounded and cannot override tenant, batch, operation, provider, subject, scope, environment, digest, result, or evidence identity.

Health endpoints are `/health/live` and `/health/ready`. Readiness requires both Redis callback/evidence stores, live S3 `HeadBucket`, versioning `Enabled`, Object Lock `Enabled`, an enabled symmetric `ENCRYPT_DECRYPT` KMS key, a ciphertext-only `GenerateDataKeyWithoutPlaintext` permission probe, and the API's authenticated evidence-sink preflight proving that the same rotating bearer principal owns both `evidence:register` and `external-event:apply` for the configured tenant. Results are cached for at most 30 seconds and every incomplete or unavailable dependency fails closed. Callback delivery leases are owner-token protected and completed entries are retained for seven days, covering the configured provider retry window. S3, provider, commerce-binding, and API failures still fail individual callbacks with a retryable 503; no third-party receipt is synthesized.
