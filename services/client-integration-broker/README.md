# Client integration broker

This service is the production integration boundary used by both `HttpWechatIdentityBroker` and `HttpResumableUploadBroker` in the API. It implements the exact `/v1/wechat/sessions*`, `/v1/media/uploads*`, `/v1/media/intakes/resolve`, `/v1/media/assets/:mediaReference/delete`, and `/health/ready` wire contracts. Every non-health request requires a bearer token whose SHA-256 digest is allowlisted; raw workload tokens are never configured in environment variables.

The WeChat login flow calls the official `https://api.weixin.qq.com/sns/jscode2session` endpoint with an AppSecret reread from a read-only projection. The raw WeChat `session_key` is immediately reduced to a SHA-256 binding. The verified identity is sent over HTTPS to the enterprise IdP, which alone chooses `actorId`, `tenantId`, roles, purpose, access token, expiry, refresh, and revocation behavior. This broker never signs or fabricates a client session. The IdP receives the original idempotency key and owns authoritative request deduplication. Redis retains broker session responses for at most five minutes and never beyond their IdP expiry; production Redis must additionally provide TLS, authentication, encryption at rest, backup controls, and an approved data-retention policy.

Media uploads use Redis-persisted, schema-versioned state bound to the full tenant/actor/roles/purpose fingerprint; roles are canonicalized as a sorted, deduplicated set, so reordering is stable while any role addition or removal changes the binding. An owner-token Redis lease serializes append, complete, and cancel operations and is renewed while work is active. AWS S3 Multipart Upload uses per-part SHA-256 checksums and server-side encryption with the configured KMS key. Completion first records a recoverable `completing` state, treats an existing KMS object as recovery from a lost CompleteMultipartUpload response, streams the whole object to verify the declared SHA-256 and exact byte count, then validates JPEG magic and fully decodes the image through libvips/Sharp with bounded dimensions and pixels. The decoded pixels are re-encoded without EXIF, XMP, ICC, or comments. The canonical object is stored with a whole-object SHA-256 checksum and KMS encryption, read back, and checked against that digest before the upload becomes `available`. Persisted lineage binds the uploaded source SHA-256 to the canonical SHA-256. Digest, decode, an explicit scanner safety rejection, or canonical-readback failures delete the object and record a terminal failed state. Scanner authentication, configuration, conflict, capacity, and availability failures keep the completed object and recoverable verification state; the same idempotency key can succeed after recovery. Cancellation aborts the multipart upload and deletes an object if completion may already have occurred. Clients receive an opaque `mediaReference`, never a bucket, object key, upload-provider ID, URL, or storage credential.

Once completion is available, the broker writes `ltm.media-asset.v2` to a separate Redis asset namespace with no TTL. Each record binds the classification, retention deadline, encryption requirement and ordered deletion-target set to the SHA-256 of an Ed25519-verified policy catalog. The catalog also binds issuer and environment; production startup accepts only the configured production issuer, key ID and environment. B05 accepts only an opaque `mediaReference` plus reason. It never accepts classification, retention or target names from a caller. The owner/data subject (when the signed policy permits it), a step-up privacy officer, or a platform administrator can request deletion; tenant and owner authority are independently rechecked in the broker.

Deletion first persists `deletion_pending`, then executes the exact closed target registry. S3 primary and derived-prefix targets enumerate every version and delete marker, independently check Object Lock legal-hold and retention state, delete each version without governance bypass, and re-enumerate to prove absence. Ambiguous Object Lock responses fail closed; an exact-object scan also bounds non-matching prefix siblings so enumeration cannot silently escape its work limit. Configured HTTPS downstream targets must return an Ed25519 receipt bound to the deletion request, nonce, tenant, media reference, canonical digest, policy digest and target ID. Each successful target receipt is CAS-persisted before the next target runs. Failure or Object Lock persists a bounded attempt, retry deadline and alert and remains pending; it is never projected as success. Retry and the maintenance reconciler execute only missing targets, and scheduled reconciliation honors the persisted retry deadline. The final tombstone exists only when its receipt IDs exactly equal the policy target set. Application legal holds require reason, authority and optional expiry, and release requires a second reason and authority. A lost response, restored S3 version, or failed remote-backup revalidation is CAS-quarantined back to `deletion_pending` and reconciled idempotently; deleted media cannot be resolved through an old intake cache.

Short-lived media URLs are Ed25519-signed and bind tenant, asset, canonical digest, audience, authenticated purpose, issue time and expiry (maximum 15 minutes, production default 5 minutes). The URL route revalidates the token and current `available` asset before reading S3 and checks the whole-object digest again. `/v1/media/lifecycle/maintenance` runs retention expiry and pending/reappearance reconciliation, while `/v1/media/lifecycle/orphan-scan` produces a bounded evidence digest and candidate list without deleting an unowned object automatically. Production also schedules maintenance per configured tenant. `/v1/media/lifecycle/authority` exports the verified `mediaLifecycleCatalogSha256` and signed-receipt `mediaSafetyPolicySha256` used by the B127 release subject. Production Redis must use persistence appropriate to this authority (AOF or equivalent durable managed configuration), encryption at rest, backups, restore testing, and a policy that does not evict asset keys.

Canonical media must also pass an independently operated HTTPS malware/content/face scanner. In production its v3 receipt is Ed25519-verified and must exactly match the pinned provider, environment, policy ID and SHA-256, model version, key ID, nonce, tenant, actor, media reference and canonical digest. Every scan and participant-mapping request carries a fresh server-generated nonce. Participant mapping additionally binds the accepted scan evidence ID and ordered participant/face-subject lists. Scanner JSON is read incrementally and the stream is cancelled as soon as an undeclared chunked body exceeds 64 KiB. Only an explicit HTTP 422 is a safety rejection; 401/403/404 are configuration failures, 408/409/425/429 and 5xx are retryable dependency failures, and other non-success statuses never become safety evidence. Face count alone never completes participant mapping. `/v1/media/intakes/resolve` returns only a fixed projection and rechecks tenant/actor/principal ownership. Its required idempotency key is scoped to the full principal and fingerprinted over the media reference plus ordered participants, so a retry cannot repeat identity review or rebind its subjects; cached results live for at most ten minutes and never beyond the mapping evidence's fifteen-minute freshness window. B08 and B14 consume the persisted accepted B07 record rather than caller-provided safety claims.

Production startup requires all of the following:

- `APP_ENV=production`, `HOST`, and `PORT` (8443 in Kubernetes).
- `LTM_BROKER_TLS_CERT_FILE`, `LTM_BROKER_TLS_KEY_FILE`, and `LTM_BROKER_TLS_CA_FILE` mounted read-only. The certificate SAN must include `ltm-client-integration-broker`, `ltm-client-integration-broker.ltm-production`, `ltm-client-integration-broker.ltm-production.svc`, and `ltm-client-integration-broker.ltm-production.svc.cluster.local`. The API mounts the issuing CA and sets `NODE_EXTRA_CA_CERTS`; internal TLS verification is not disabled.
- `LTM_BROKER_WORKLOAD_TOKEN_SHA256S`, containing one to eight lowercase SHA-256 digests for currently valid API workload tokens. Rotation can overlap two digests.
- `LTM_WECHAT_APP_ID` and `LTM_WECHAT_APP_SECRET_FILE`; the secret file must not be group/world writable.
- `LTM_ENTERPRISE_IDP_URL` and `LTM_ENTERPRISE_IDP_TOKEN_FILE`; the URL must be a credential-free HTTPS origin and the projected token is reread on each request.
- `LTM_BROKER_REDIS_URL` using authenticated `rediss://` in production.
- `LTM_MEDIA_S3_BUCKET`, `LTM_MEDIA_S3_REGION`, `LTM_MEDIA_S3_KMS_KEY_ID`, and optionally `LTM_MEDIA_S3_PREFIX`.
- `LTM_MEDIA_SAFETY_SCANNER_URL`, `LTM_MEDIA_SAFETY_SCANNER_TOKEN_FILE`, `LTM_MEDIA_SAFETY_RECEIPT_PUBLIC_KEY_FILE`, `LTM_MEDIA_SAFETY_EXPECTED_PROVIDER`, `LTM_MEDIA_SAFETY_EXPECTED_POLICY_ID`, `LTM_MEDIA_SAFETY_POLICY_SHA256`, `LTM_MEDIA_SAFETY_EXPECTED_MODEL_VERSION`, `LTM_MEDIA_SAFETY_EXPECTED_KEY_ID`, and `LTM_MEDIA_SAFETY_EXPECTED_ENVIRONMENT=production`. These are mandatory in production; a scanner URL without the complete signed-receipt authority is rejected at startup.
- `LTM_MEDIA_LIFECYCLE_CATALOG_FILE`, `LTM_MEDIA_LIFECYCLE_TRUST_PUBLIC_KEY_FILE`, `LTM_MEDIA_LIFECYCLE_EXPECTED_KEY_ID`, `LTM_MEDIA_LIFECYCLE_EXPECTED_ISSUER`, `LTM_MEDIA_LIFECYCLE_EXPECTED_ENVIRONMENT=production`, and `LTM_MEDIA_LIFECYCLE_TARGET_SECRET_ROOT`. The bounded catalog is verified before the server listens and must contain a closed raw policy and known target registry. HTTPS target credential and receipt-key paths are confined to that dedicated read-only root and validated at startup; they cannot point at TLS, IdP, scanner, or download-signing secrets elsewhere in the container.
- `LTM_MEDIA_DOWNLOAD_PRIVATE_KEY_FILE`, `LTM_MEDIA_DOWNLOAD_PUBLIC_KEY_FILE`, `LTM_MEDIA_DOWNLOAD_BASE_URL`, `LTM_MEDIA_DOWNLOAD_ISSUER`, and optionally `LTM_MEDIA_DOWNLOAD_MAXIMUM_TTL_SECONDS` (30-900).
- `LTM_MEDIA_LIFECYCLE_MAINTENANCE_TENANT_IDS` and optionally `LTM_MEDIA_LIFECYCLE_MAINTENANCE_INTERVAL_MS`. Production requires at least one explicit tenant; the task never assumes cross-tenant authority.
- AWS workload identity/IRSA granting only the bucket multipart/read/delete actions and KMS encrypt/decrypt/data-key actions for the configured prefix and key.

Request bodies, headers, dependency JSON, response JSON, upload size, chunk size, decoded dimensions, pixel count, timeouts, role vocabulary, identifiers, session lifetime, and redirect behavior are bounded. Dependency failures and malformed persisted records fail closed. `/health/ready` reports separate Redis/upload, durable media-asset registry, S3, IdP, WeChat-secret, and media-scanner checks and returns 503 unless every check succeeds; it is operational evidence only, not external certification.

Run `pnpm --filter @ltm/client-integration-broker test` for injectable protocol and state-machine tests. Those tests use fake Redis/S3/fetch transports and cover bearer rejection, IdP authority, session credential TTL, tenant/actor isolation, role-set binding, concurrent writers, completion-response loss, scanner dependency recovery with the same idempotency key, exact nonce/subject response binding, 64 KiB stream cancellation, digest mismatch deletion, fake-JPEG rejection, metadata removal, source-to-canonical lineage, canonical readback, upload-TTL-independent resolution, S3 deletion, durable tombstones, deletion-response loss recovery, KMS/checksum command construction, and unsafe secret projections. Production bootstrap always constructs the real Redis client, AWS SDK S3 client, and global HTTPS `fetch`; live provider/cluster acceptance remains `NOT_RUN` until executed in the target environment.
