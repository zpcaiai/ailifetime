# WeChat identity authority

Dedicated deployment: `ailifetime-wechat-identity` in the already authorized Vercel team. The authority exchanges real `wx.login` codes only with `https://api.weixin.qq.com/sns/jscode2session`, binds identities to durable PostgreSQL actor/tenant rows, and issues ES256 access JWTs accepted by the API's existing pinned JWT/JWKS verifier. It implements the API identity-broker wire contract; it does not provide an interactive OAuth authorization flow.

The three tables in `infra/wechat-identity/001_identity.sql` use FORCE RLS keyed by the configured AppID. Runtime credentials have no superuser, BYPASSRLS, role creation or schema mutation authority. Migration/owner credentials are never installed in the function. Provider credentials and cached responses are AES-GCM encrypted with request/session binding; raw OpenID/session_key, roles and tenant choices never come from client request fields. The only initial role is consumer and purposes are a closed server-side list.

The function requires `DATABASE_URL` (`sslmode=verify-full`), `LTM_WECHAT_APP_ID`, `LTM_WECHAT_APP_SECRET`, `LTM_IDENTITY_ISSUER`, `LTM_IDENTITY_AUDIENCE`, `LTM_IDENTITY_CONSENT_VERSION`, `LTM_IDENTITY_SIGNING_JWK` (private P-256 JWK), `LTM_IDENTITY_ENCRYPTION_KEY` (32 random bytes, base64url), and `LTM_IDENTITY_WORKLOAD_TOKEN_SHA256`. Set these as production-only Vercel Secret/Sensitive variables. Never put them in the mini program, public deployment artifacts, repository or chat. The API retains the corresponding workload token; the issuer stores only its digest. The currently deployed issuer URL is `https://ailifetime-wechat-identity.vercel.app` and its public key set is `/.well-known/jwks.json`.

POST `/v1/wechat/sessions` accepts exactly code, consentVersion and clientRequestId, with a workload bearer and idempotency-key. The SQL intent commits before external code exchange. Duplicate keys with changed input conflict; uncertain/rejected exchanges require a fresh code and request, and never silently retry a consumed code. Provider replies and request bodies are bounded. A caller cannot choose the exchange endpoint. HTTP loopback is available only through an explicit constructor argument under the test environment.

POST `/v1/wechat/sessions/refresh` and `/v1/wechat/sessions/revoke` require the workload bearer and `x-ltm-subject-token`. Refresh rotates once, preserves idempotence, and caps the session family at 24 hours. Logout immediately prevents refresh and clears retained provider credentials. Access JWTs expire after five minutes. The existing API verifies JWTs offline, so logout does not instantly revoke an already issued API token; remaining API access is bounded by its expiry. Provider session-key ciphertext is cleared on rotation/logout and opportunistically after expiry. No claim is made that database history/backup copies are physically erased at that instant. Future virtual-payment signing needs a separately verified fresh WeChat session.

GET `/health/live` reports a running handler; authenticated `/health/ready` checks required configuration, key loading, restricted DB role, all three tables and FORCE RLS. It cannot prove AppSecret validity without a real fresh WeChat code. Missing AppSecret returns503. Public JWKS contains no private JWK fields. No synthetic user, static principal, admin claim or fabricated successful session exists in the production handler.

Build with `pnpm --filter @ltm/api build`. `node tools/vercel-identity-package.mjs ABSOLUTE_NEW_DIRECTORY` bundles only this handler and produces exactly three deployment files, using the already pinned pg/jose dependencies. No secrets, photos, source checkout or cron are uploaded. Deploy to the dedicated existing project and re-deploy after environment changes. The main business API is deployed separately; its OIDC issuer/JWKS, broker URL/workload token and remaining production dependencies must be wired and verified before real mini-program login is accepted. Keep the mini-program API origin pointing to its enrolled business API, not this internal identity service.

Tests use a dedicated disposable PostgreSQL database named `ltm_identity_test`, a least-privilege `ltm_identity_test_runtime` role and a synthetic external WeChat HTTP boundary. Supply `LTM_IDENTITY_TEST_POSTGRES_ADMIN_URL` and `LTM_IDENTITY_TEST_POSTGRES_URL`; test setup refuses a different database or non-loopback host. These real HTTP/SQL/JOSE tests are not official WeChat or phone acceptance. Real code exchange, legitimate domain enrollment, main API wiring, and real-device login remain separate unfinished checks until actually run.
