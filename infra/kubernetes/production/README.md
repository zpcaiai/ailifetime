# Production Kubernetes contract

These manifests are production templates, not proof that a cluster or external provider exists. Render them with `node tools/kubernetes-production.mjs render ...`; the renderer rejects mutable image tags and unresolved values, then performs static restricted-workload checks.

The renderer also requires `--oidc-authorization-endpoint`,
`--oidc-token-endpoint`, `--oidc-client-id`, `--oidc-redirect-uri`, and
`--oidc-scopes`. Both endpoints must be exact public HTTPS paths on the
`--oidc-issuer` origin, the redirect must exactly equal
`https://<host>/auth/callback`, and scopes must include `openid` while excluding
`offline_access`. The IdP registration is a public SPA client with no secret and
must allow `https://<host>` to call the token endpoint through CORS. Rendering
validates configuration shape; deployed CORS behavior and issuer reachability
still require signed production evidence.

Before applying the rendered directory, the deployment owner must provision these external objects through the platform secret/config controller:

- `ltm-production-database`: `runtime-url` for the non-owner `NOBYPASSRLS` application role and `migrator-url` for a dedicated non-superuser migrator role. Both URLs use `sslmode=verify-full`.
- `ltm-production-api`: `metrics-token-sha256` and `evidence-trust-keys-json` containing public keys only.
- `ltm-production-consent-policy`: a signed closed `catalog.json` and `trust-keys.json` containing only Ed25519 public trust keys. The API mounts the catalog read-only, verifies its signature/environment/validity at startup, and derives jurisdiction `CN` plus locale `zh-CN` from the server ConfigMap; callers cannot override either value.
- `ltm-production-client-brokers`: short-lived `wechat-identity-token` and `upload-broker-token` workload credentials. The API rereads their read-only projected files for every broker request; neither token belongs in a ConfigMap or image.
- `ltm-production-client-integration-broker`: authenticated `rediss://` URL, one or two API workload-token SHA-256 digests for rotation, WeChat App ID, enterprise IdP HTTPS origin, S3 bucket/region/KMS key/prefix, and the workload-identity role configuration. The approved media-safety scanner HTTPS origin is a required renderer input (`--media-safety-scanner-url`) and is emitted directly as non-secret configuration. Redis is also the durable media-asset/tombstone authority: it must use managed persistence (AOF or an approved equivalent), encryption at rest, backup/restore controls, and a non-evicting policy for the broker namespace; its credential/session retention must be approved. Raw API workload tokens do not belong in this object.
- `ltm-production-client-integration-broker-credentials`: `wechat-app-secret` and `idp-token`, both continuously rotated and projected read-only.
- `ltm-production-client-integration-broker-scanner-credentials`: the independently operated scanner workload credential in `token`, continuously rotated and projected read-only. The token is never a renderer argument, environment value, ConfigMap value, image layer, or workflow input.
- `ltm-production-client-integration-broker-tls`: `tls.crt`, `tls.key`, and issuing `ca.crt`. The certificate SAN covers the fixed `ltm-client-integration-broker.ltm-production.svc` service DNS name. The API receives only `ca.crt` and uses `NODE_EXTRA_CA_CERTS`; TLS verification is never disabled.
- `ltm-production-client-integration-broker-egress-ca-bundle`: `idp-ca.crt`, `scanner-ca.crt`, and `ca-bundle.pem`. The approved certificate/trust controller must construct `ca-bundle.pem` by concatenating the complete enterprise IdP and media-scanner CA chains; the two source keys are retained for auditable provenance. The broker points its single `NODE_EXTRA_CA_CERTS` value only at `ca-bundle.pem`, so neither trust chain can silently replace the other. Use the approved public-root chain for either source when that dependency does not use a private CA.
- `ltm-production-workers`: the five route adapters, 18 external-command batch adapters, metrics-token hash and their managed secret references. B10 serves both publish and provider revoke, so startup and the managed gateway policy jointly cover 19 fixed callback route contracts.
- `ltm-production-integration-gateway`: TLS Redis URL, S3/KMS/Object-Lock settings, evidence issuer/key references, commerce binding configuration and enabled provider settings. It contains references, never inline private keys.
- `ltm-production-integration-gateway-api-token`: a short-lived external-IdP OIDC service token in `token`, continuously rotated by the approved external-secret controller. A Kubernetes service-account token is not substituted for the configured API issuer.
- `ltm-production-tls`: certificate provisioned by the approved cluster certificate controller.

The projected cloud service-account tokens require a cluster workload-identity configuration. The client broker token uses the `sts.amazonaws.com` audience and its cloud role is restricted to the configured S3 prefix and KMS key. The renderer requires canonical private PostgreSQL/Redis CIDRs and exact ports so NetworkPolicy does not expose database protocols to arbitrary destinations; separate policies allow only API-to-broker TCP 8443. The scanner renderer value must be a credential-free DNS HTTPS origin on the default TCP 443 port, and static validation proves that the existing HTTPS egress policy selects the client broker and permits exactly TCP 443. A missing scanner URL fails rendering; a missing scanner credential or merged CA Secret/key prevents the Pod from starting; scanner readiness failure keeps the Deployment unready. Namespace creation, external secret synchronization, certificate issuance, broker DNS SAN validation, ingress-controller identity, destination-aware cloud egress controls, Redis encryption/backup, registry pull policy, monitoring, backup service and environment approval remain deployment-platform responsibilities and must produce signed evidence. Apply the migration Job and wait for its successful completion before rolling out the four Deployments. Applying a template does not change `NOT_CERTIFIED`.

The independently operated deployment-assurance collector is outside these application workloads and is not granted by this template. Before B127 can pass, the platform must give that collector a narrowly scoped production workload identity, trusted TLS client certificate and network path to the public API plus the broker service. It must capture the raw authenticated broker `/v1/media/lifecycle/authority` response into the release artifact store and produce the closed `runtime-policy-authority` report: API and broker `/health/ready` responses, API `/v1/consent-policy/authority`, broker `/v1/media/lifecycle/authority`, raw response SHA-256 values, workload identity/mTLS verification, production environments and all three release-policy digests. The deployment-evidence signer then binds that report to the exact manifest and release-subject hashes; application configuration alone cannot satisfy the check.

The manual `production-release-candidate` workflow is intentionally non-deploying. Configure the GitHub environment named `production-release-approval` with required reviewers and protected-branch rules before enabling it. Environment approval lets the workflow render a checksum-bound candidate, but does not count as B127 release approval, cluster deployment evidence, penetration-test evidence, legal approval or disaster-recovery certification.
